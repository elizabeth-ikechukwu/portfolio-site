  • TaskFlow: a task management platform that deploys itself

    Sole engineer. 10 weeks. Node.js API, React frontend, Kubernetes on AWS EKS.

    Most teams lose days to deployments: someone signs in to a server, pulls an image, restarts a container, and hopes. TaskFlow was built to remove that person from the loop entirely.

    Nothing reaches production without passing 6 gates. Every push runs lint, unit tests, build, a Trivy scan, integration tests, then publish. The scan blocks on CRITICAL and HIGH vulnerabilities, so a bad image fails the build instead of landing in the registry. It works: one run stopped on 6 high-severity findings, which I traced to npm's own dependencies in the Node base image and documented against each CVE with a review date.

    There are no AWS credentials to leak. GitHub Actions signs in through OIDC and gets credentials that expire when the job ends. Every pod assumes its own scoped IRSA role, 6 in total. Secrets live in SSM Parameter Store and reach the pods through External Secrets Operator on an hourly refresh, so no developer ever handles a real credential. Port 22 is closed on every instance and deployment runs through SSM Session Manager, so there are no key pairs and every session lands in CloudTrail.

    CI cannot write to Git, and still ships. ArgoCD Image Updater watches ECR and promotes the new SHA-tagged image itself. That keeps branch protection on main intact with no bypass, and every running container traces back to the exact commit that built it.

    The cluster corrects itself. 3 nodes across 2 availability zones, HPA scaling each service from 2 to 5 replicas, PodDisruptionBudgets holding 1 replica up during maintenance, NetworkPolicies allowing the backend to accept traffic only from the frontend and ALB health checks. ArgoCD reverts any manual change back to what Git says within a sync cycle.

    Things that actually broke, and what they taught me:

    • ECR returned 403 after OIDC succeeded. Authentication passed, authorization didn't. The policy was missing 2 actions buildx needs to check existing layers.
    • The EBS CSI driver crash-looped because it was using the node role instead of its own IRSA role.
    • Pods couldn't reach RDS. The security group allowed the node security group, but the VPC CNI assigns pods their own IPs.
    • Prometheus was OOMKilled on startup during WAL replay, fixed by right-sizing the limit rather than the node.
    • ArgoCD silently applied only namespace.yaml because it wasn't recursing into subdirectories.

    The EKS cluster is torn down to keep running costs at zero. The live demo serves the same images from a single EC2 instance, and one terraform apply brings the full platform back.

  • PulseOps: an incident management platform for multiple organisations, with isolation proven by a test

    Sole engineer. Live at pulseops-app.online.

    When an incident ends, most teams lose the next hour reconstructing what happened: who was paged, when it was acknowledged, what actually fixed it. PulseOps writes that record as the incident happens. Declare, tag severity, track it on a live timer, and when it resolves a blameless postmortem is generated pre-filled with the real timeline and response times.

    Multi-tenant means isolation has to be proven. Every organisation's incidents sit in one database. One test asks for another organisation's incident using its exact record ID and expects a 404, not a 403, because 403 would confirm the record exists. It is asserted on read, on status transition and on delete. That test is 1 of 29 running in GitHub Actions on every push, covering auth, tenant boundaries and the incident lifecycle.

    The isolation sits in the query itself. Auth verifies the token and extracts the organisation, then every query in the data layer runs scoped to it. There is no code path that reaches a row without an organisation attached.

    2 pipelines, 2 identities, 0 stored credentials. Terraform assumes an infrastructure role and the deploy workflow assumes a narrower one scoped to application deploys. Both sign in through OIDC. JWT secrets and the database password live in SSM Parameter Store.

    The bug I am most glad I found. Mid-build, Terraform and the deploy pipeline were both authoritative over which image version was running. Nothing had failed yet, but the next routine infrastructure change would have rolled back a working deploy silently, with no error and no alert. I traced it and split ownership so each system controls only what it should. That class of bug does not announce itself, it just quietly undoes a release.

    Infrastructure is Terraform throughout: a VPC across 2 availability zones, RDS PostgreSQL in private subnets, ElastiCache Redis, ECS on EC2, ECR scanning every image on push, Route53. Every merge to main tags the image with the commit SHA and rolls out a new task revision. HTTPS was added after launch on live infrastructure with no downtime, using Certbot and a Route53 DNS challenge.

    It is also the product behind the customer success case study on this site, so I run the customer side of the system I built.

  • Banking platform: the infrastructure 3 teams deployed onto

    Infrastructure team lead, Digital Witch Pod 13. April to May 2026.

    Pod 13 built and shipped a 3-tier banking application: a React frontend, a REST API handling auth, accounts and transactions, and a MySQL database. Frontend and backend teams owned their services. I led the infrastructure team and owned everything those services ran on.

    4 Terraform modules, no console-created resources. A VPC with 6 subnets across 2 availability zones split into public, private and database tiers, an EKS 1.32 cluster with a node group scaling from 2 to 6 nodes, RDS MySQL in private subnets with no public endpoint, and Route53 with ECR. State lives in S3.

    Delivery runs through the pipeline. A pull request to main runs fmt, validate and plan so the team reviews the diff before anything changes. Merging runs apply. ArgoCD then syncs both services onto the cluster, behind nginx ingress, with cert-manager issuing Let's Encrypt certificates for the 3 subdomains.

    The worst day was losing the Terraform state. The S3 bucket holding it was deleted, so Terraform no longer knew about a single resource it had created, including a running EKS cluster. I recreated the bucket and enabled versioning, so state is recoverable instead of rebuilt from scratch.

    Then the backend team hit pods that could not reach the database. Their credentials were fine. The RDS security group had no rule allowing the node group in on 3306. That fix was mine, and it is the kind of problem that stalls a team until someone owns both sides of the boundary.

    One thing worth stating plainly: this pipeline authenticated to AWS with access keys in GitHub secrets. On my own builds since, that is replaced with OIDC and no static credentials exist anywhere.

  • Incident response: 4 outages on a live server, caught and fixed inside SLA

    Solo build. AWS EC2, Datadog, Nginx, Bash.

    Monitoring that has never fired is a guess. This project existed to prove the alerting worked by breaking things on purpose and handling each one properly.

    4 incidents, all detected automatically. Nginx process down, CPU at 95%, disk past 80%, and an HTTP 502 caught by a synthetic check. Datadog picked up each one in 1 to 11 minutes, fixes took 3 to 43 minutes, and every one closed inside its SLA.

    Every alert arrives with its own runbook. The Slack message carries the immediate checks to run, the remediation script path, and a link to the runbook in the repo. Whoever is on call does not have to work out where to start, which is most of the time lost in a real incident.

    The synthetic check blocks the pipeline. An HTTP test runs against the site every minute, and a failure stops the CI/CD pipeline rather than letting the next deploy land on a service that is already broken.

    The most useful thing I found was in the monitoring itself. While working the disk incident, I found the alert was watching the wrong disk. It would have stayed quiet through the exact failure it was written for. That is the point of running drills: the monitor is code, and code has bugs.

    The fixes run themselves. A cron job checks CPU every 5 minutes and terminates runaway processes, and a nightly job clears disk at 02:00. Both log every run, so there is a record of what the system did while nobody was watching. Each incident also has a written report and runbook, so the manual path exists when the automatic one is not appropriate.

  • Distributed inference on AWS: running a language model across 3 machines

    Built as a take-home for an internship application. Terraform, Docker, Python, TypeScript.

    Running a model on one box is easy. The work is splitting it across machines that have to find each other, stay connected, and keep the model off the public internet.

    Only 1 machine is reachable from outside. Nginx sits on a public host and takes requests on port 80. The 2 worker machines live in a private subnet with no inbound route, reaching out through a NAT gateway only when they need to. A request arrives at Nginx, goes to the engine, and is handed to whichever worker can serve it over a WebSocket connection on the internal network.

    The machines are sized for what they do. The caller worker runs TypeScript on a t3.small. The inference worker runs a Gemma model in Python on a t3.medium, because the model needs the memory and nothing else does. Paying for the larger instance twice would have been the easy mistake.

    The whole thing is Terraform, with one compose file per machine. VPC, subnets, NAT, security groups, instances and their user data. Nothing was clicked together, so the reviewer could rebuild it from the repository and get the same 3 machines.
